## 0. 三十秒版

Exuvia 是一个**面向 AI Agent 的 Android 通用脱壳 / 代码恢复流水线**。

- **输入**：一个加壳 APK
- **输出**：一个可续作的 handoff 工作区（脱壳产物 + 欠账清单 + 证据切片 + 验证工具 + 报告索引）
- **形态**：确定性二进制 CLI，静态优先，不注入、不运行目标 App
- **名字**：Exuvia（蝉蜕）——壳留在原地，代码恢复生命
- **口号**：*"Separate the shell from what lives inside."*

**项目当前状态：spec 阶段。** 尚无实现代码。第一个 commit 应该是三份契约（见第 6 节），不是源码。

## 2. 问题定义与立项依据

**成本模型**：所有混淆/加固都只是提高成本，没有绝对不可破解。当前破解成本 = 分析员时间 + LLM token 费用。本项目目标是**大幅摊销这个成本**：把"每个壳都要 LLM 从头探索一次"变成"按已固化的 SOP 低成本复用"。

**实证依据**（接手者应知道的三个事实）：
1. Carleton 大学 2025 年论文（12,341 App 测评）：现存开源脱壳器（BlackDex、frida-dexdump 等）面对现代商业加固**已全部失效**。赛道有空窗。
2. FreeBuf 2026-10 MiniMax 静态脱壳实测：LLM 纯静态（无 adb/Frida）可脱壳，但首例约 2 小时 / 80M token / 人工接管 2 次；沉淀为 SOP 后同类样本"游刃有余"。**贵的是首次探索，不是解密本身。**
3. 360SRC 的 VMP 分析文章：JNI trace 蒸馏后交 LLM 可还原 VMP 方法，简单函数可完美还原。

**已接受的宿命**：这是猫鼠游戏。目标不是"永久解决"，而是**适应速度**——这是唯一能赢的指标。工具火了之后壳厂商会加反 Exuvia 检测，应对方式是模块化对抗层 + 快发布节奏。

## 3. 架构

### 3.1 三轨道

```
轨道A 静态分析   —— 解包、指纹、so 切片、解密例程定位与离线复现（MVP 全部）
轨道B 模拟执行   —— Unicorn/qiling 离线跑 so 里的解密函数（动态的语义、静态的安全属性）
轨道C 定点动态   —— 仅对指定方法注入调用/trace（VMP 类的最后手段，最小化 per-method 工具）
```

优先级永远 A > B > C。轨道 B 是精髓：不注入、不运行目标 App、完全确定性、CI 可跑——反调试/反 Frida/完整性校验根本没机会触发。

### 3.2 分层交付（每个方法声明它到达的层级）

| 层级 | 产物 | 成本 | 说明 |
|---|---|---|---|
| L1 | 骨架 DEX：类/方法签名齐全，方法体为 native stub 指向原 so | 极低 | **性价比最高**，App 结构立刻可导航（jadx 可开） |
| L2 | 伪代码还原：Ghidra headless + JNI 语义标注 + 动态 trace 交叉验证 | 中 | 能读懂方法逻辑、API 调用序列 |
| L3 | 可重编译源码：语义还原 + 差分验证 | 高 | 可重打包、可修改 |

覆盖率报告按 L1/L2/L3 分层统计。大部分分析需求到 L1+L2 就结束了。

### 3.3 v0.1 MVP 竖切（窄而完整，勿扩大）

```
APK 解包 → 壳指纹（技术族命名）→ so 函数切分 → 解密例程候选定位
→ 切片喂 LLM 复现算法（工具做：密码学常量扫描[AES sbox/Blowfish P数组等可识别字节模式]、
   JNI_OnLoad 交叉引用、加密 asset 引用图）
→ 离线解密 → DEX 修复 → L1 骨架 → debt 清单 → handoff + 静态脱壳脚本
```

- 目标壳：**一代壳（整体加密）**，验收 20 样本
- Android 版本：先锁一个（arm64 + 单版本），但 hook 点按 ART 版本分文件组织，为扩展留缝
- **静态脱壳脚本本身是一等交付物**：可复现、可审计、自验证，是 handoff 里最强的证据形式，也是回归语料的组成部分（壳更新 → 老脚本失败 → 精确定位变化点）

## 4. handoff 契约（项目灵魂）

交付物不是"报告"也不是"半成品"，是**可续作的工作区**。报告只是它的索引。

```
handoff/
├── workspace/        # 已完成产物：dex、修复结果、符号、切片（按方法组织）
├── debt.json         # 欠账清单：每个未完成方法的事实 + 难度信号 + 建议 SOP
├── evidence/         # 证据切片：JNI trace、opcode 流、反编译片段（按方法索引）
├── attempts.log      # 尝试日志：试过什么、为什么失败（下游不会重复死过的路）
├── verify/           # 验证工具：差分测试脚本、动态对账 hook
└── REPORT.md + .json # 人类可读摘要 + 机器可读索引（指向以上所有）
```

**debt.json 的语义（曾被修正，见第 8 节）**：工具是确定性二进制，**不知道**一个方法要烧多少 token。所以输出的是**事实 + 难度信号**（native stub 的 JNI 调用数、opcode 熵、VM handler 数量），"价格"由下游 AI 估。**不要给 debt 加"预估成本"字段。**

**回流协议**：下游完成的方法合并回 workspace，debt.json 销账，attempts.log 追加记录（`unpack merge <dir>` 子命令）。多轮、多 Agent 共享同一状态增量推进——这决定了项目是"一次性工具"还是"可续作工作台"。

**目标导向停止条件**：`--goal` 参数（如"搞清支付签名算法"）。无目标默认做到 L1，欠账全部标价挂起；有目标则 debt 按相关性排序，无关方法标 `skip`。"要不要继续完成"不是流水线决定的，是报告里每条欠账的信号让下游（或用户）决定的。

## 5. CLI 契约

**默认体验 = 拖入即用**：`exuvia app.apk` → 产出 handoff 目录。全程零提问（非交互是硬约束，任何交互式 prompt 都直接杀死 Agent 场景）。

**参数清单（v0.1 就这六个，每个都有设计来源，勿随手增删）**：

| 参数 | 来源（对应的设计决策） |
|---|---|
| `--version` | 常规 |
| `--profile <file>` | 判断必须外置，不能走私进代码 |
| `--goal "..."` | 停止条件由目标决定 |
| `--json` | CLI 就是 API（不做 MCP 的代价） |
| `--resume` | 幂等、可断点续跑 |
| `unpack validate <dir>` | 下游自检 handoff |
| `unpack merge <dir>` | 回流协议 |

**参数纪律**：
- 三次法则：同一需要出现第三次才配升级为参数
- 默认路径服务人类，显式参数服务 Agent；**任何功能都不允许只能靠参数触达**
- 环境发现（jadx/ghidra 路径等）走自动探测 + 环境变量 + profile，不占 CLI 参数位

**退出码语义（与架构一致）**：欠账是正常产出不是失败——handoff 里有 debt 也返回 0；只有连 L1 骨架都产不出来才非零。**别用退出码惩罚架构上鼓励的行为。**

**Agent 人体工学（不做 MCP 的补偿，必须扛住）**：`--json` 全覆盖、稳定退出码、无 TTY 假设、幂等、机器可读的错误输出（报错是给 Agent 看的）、schema 随包分发（`$id` + 版本号）。

## 6. 三份契约优先于代码

**第一个 commit 是 spec，不是源码**（接口先于实现——工具是给下游 AI 的契约，契约本身也该先于工具存在）：

1. **handoff 的 JSON Schema**（版本化，`$id`）
2. **CLI + SKILL 语义**（幂等、退出码、schema 版本号；SKILL 版本化并和 schema 锁死，如 `requires: handoff-schema >= 1.2`）
3. **profile 格式**（扫描深度、什么算可疑 DEX 头、方法分类阈值——全部配置化）

## 7. 设计原则（⚠️ = 反直觉，最容易被"好心破坏"）

1. **⚠️ 工具不做终审。** 方法层：debt 只给事实和难度信号，下游决定继续不继续。工具层：profile 外置、不确定度一等输出（"疑似 DEX，头部损坏，置信 0.7"而不是默默决定）。生态层：项目不定义集成方式，只给状态和建议。**同一个哲学在三层自相似——项目自己就是它输出的 handoff 包。**

2. **⚠️ 不确定度是一等输出。** 宁可说"不知道、置信 0.7"，不要假装确定。每个工具判断写进 audit trail。

3. **⚠️ 静态优先，不选 Frida 路线是故意的。** Frida 把主战场放在对方防御最强的地方（anti-Frida 检测）。曾计划 Frida MVP，已被推翻（见第 8 节）。dump 核心写成与注入方式无关的纯模块，但 MVP 是纯静态轨。

4. **⚠️ MCP 不做。** 不是技术不行，是架构决定：引擎和集成层分离是生态常态（Ghidra/JADX 从没做过 MCP server，被第三方 wrap 是荣誉不是损失）。措辞上是"不作为核心交付物拥有"而非"拒绝"——社区 PR 的 MCP wrapper 收进 `contrib/` 单独维护，不背协议漂移债。

5. **⚠️ SKILL 是灵魂，不是文档附属品。** SKILL 承载判断力（什么时候该做什么、拿到东西怎么理解、回流纪律），CLI 是手。SKILL 必须版本化并和 schema 锁死——协议漂移比没有协议更糟。SKILL 结构：30秒版 → 工作流决策树 → handoff 解读 → 升级路径 → 版本锚点（schema 全文放 docs/，SKILL 里只放链接，别撑爆上下文）。

6. **⚠️ 参数极少是故意的。** 参数不是功能，是设计决策的逃生口（见第 5 节表格）。新参数要有明确的设计来源，不接受"这个功能很常用所以加个 flag"。

7. **技术族命名，永不写厂商名。** 内部研究当然逐厂商看，但产出的 SOP、指纹、处理器按技术命名。社区 SOP 贡献必须清洗厂商名，否则中立性声明会被贡献者稀释。

8. **交付物是"可续作状态"，不是"完成度"。** 不要诱导"推到最深处"——很多方法对分析目标无关，全脱完是浪费。停止条件由目标决定。

9. **验证闭环先于功能扩张。** 语料 = F-Droid 开源 App 自己加固（自己打包自己的 App 完全合法），原始版即 ground truth。指标：类级覆盖率、方法级覆盖率、产物可解析率（jadx 能开）、与原始 dex 字节一致性。

10. **敌意输入预期。** 分析者会拿工具跑恶意软件。文档写清"在一次性快照环境中运行"。

**v0.1 验收线**：20 个一代壳样本、类级恢复 ≥90%、下游 AI 拿 handoff 能完成 3 个规定任务（"找到 Application 子类"、"列出网络请求入口"、"恢复指定方法"）。

## 8. 决策日志（已被推翻的方案——别改回去）

| 曾计划 | 现结论 | 推翻原因 |
|---|---|---|
| Frida 形态 MVP | 纯静态轨 MVP | Frida 被厂商盯着打；静态路线已被 MiniMax/Huli 实测验证；模拟执行（轨道B）可提供动态语义而不触发防御 |

## 9. 范围边界（诚实清单，勿过度承诺）

静态/模拟**解决不了**的（进 debt 清单，标注"需轨道C"或"L3 范畴"）：
- key 从设备环境派生（IMEI、build fingerprint——模拟可伪造枚举但组合爆炸）
- 网络拉取的 payload
- 流式拼装的 DEX
- VMP 的完整语义还原（四代壳在 roadmap 中明确为轨道C 定点动态 + L3）

**四代壳（VMP/dex2c）处理原则**：原始字节码从不存在于内存，dump 原理上无解。"汇编分析还原同等功能"不是退而求其次，是换了一个正确的问题定义：交付物从"原始字节"变成"等价语义"（.NET 的 OldRod 反虚拟化是先例）。残留物是机器翻译的汇编，有固定习语（JNI 边界调用、寄存器约定、模板化控制流）——精度可以很高，且"同等功能"对分析场景是低标准（要的是 API 序列和逻辑，不是指令级一致）。

## 11. 术语表

| 术语 | 含义 |
|---|---|
| handoff | 交付给下游 AI 的可续作工作区（见第 4 节） |
| debt / 欠账 | 未完成的方法及其事实+难度信号；正常产出，不是失败 |
| 轨道 A/B/C | 静态 / 模拟执行 / 定点动态 |
| L1/L2/L3 | 骨架 DEX / 伪代码还原 / 可重编译源码 |
| 技术族命名 | 按加固技术特征（而非厂商）命名指纹与 SOP |
| 回流 | 下游完成的方法合并回 workspace、debt 销账、attempts 追加 |
| 一代壳 | DEX 整体加密（v0.1 目标）；二代=方法抽取；三代=动态解密+SO混淆；四代=VMP/dex2c |

## 12. 给接手 Agent 的行为准则

1. **动手前**：读完本文档；检查第 8 节确认你要做的事不在"已推翻"清单里。
2. **写代码时**：判断逻辑进 profile，不硬编码；每个判断写 audit trail；不确定就输出不确定度。
3. **想加东西时**：新参数过三次法则；新功能先问"这是不是第 6 节三份契约的变更"——是的话先改契约再写代码。
4. **想"优化"时**：对照第 7 节 ⚠️ 条目。如果你觉得某条原则"明显更好"，大概率它已经在第 8 节被推翻过一次。
5. **修改本文档**：可以补充事实和进度；修改原则/决策日志需要人类维护者确认。
6. **交付给下一个 Agent 时**：更新本文档的"当前状态"，像 debt.json 一样诚实记录你做了什么、什么没做完、为什么。
